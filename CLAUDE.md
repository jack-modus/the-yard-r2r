# The Yard: Rags to Riches

A horse-racing trainer sim (Next.js App Router + TypeScript + Tailwind v4, PWA target). The player is Tony Vincenzo — a fixed protagonist, not a customisable name — taken on by trainer Simon Bridges despite (or because of) his father's disgraced history in the sport, working toward a Group 1 win with a string built up one horse at a time, starting from a single pick out of six candidates. Originally prototyped as a single-file Claude.ai JSX artifact (`reference/rags-to-riches-v6.jsx`) — that file is kept for reference during extraction, is not linted as app code, and should not be imported from.

## Hard rules — do not violate these

1. **No real named people.** Rivals, jockeys, trainers, bosses, owners — all fictional, real-sounding names only. Never use a real person's name, even a retired or minor one. This avoids IP/publicity-rights risk. **Exception, by explicit user decision**: the five real British Classics (1000/2000 Guineas, Oaks, Derby, St Leger) are used by their real names in `lib/sim/calendar.ts` — these are historic race *traditions*, not people, so the publicity-rights logic behind this rule doesn't apply the same way. Don't extend this exception to other real-world racing entities without asking; it was a specific, explicit call for the Classics only.
2. **Course/track facts must be factual but never copied.** Course descriptions (`src/lib/sim/courses.ts`: `COURSES[...].line`, `INSIGHTS`) and draw-bias notes must be written fresh from general racing knowledge. Never lift wording from Racing Post, Timeform, or any other source verbatim or near-verbatim. Facts (e.g. "Chester is left-handed and tight") aren't copyrightable — expression is, so always re-derive the description in original words.
3. **No live scraping of commercial racing data.** Never scrape or ingest Racing Post/Timeform/etc. results data — ToS/licensing risk. The only real-world dataset permitted is the user's own historical race data in `C:\Users\jackr\ggs` (their existing Betfair ML pipeline), used to calibrate the sim's invented stat curves against real favourite strike-rates and SP distributions — never to source real horse/human names or copy real race commentary.
4. **No monetisation linked to the simulated betting.** Do not add a paid "Hall of Fame," loot boxes, or any real-money purchase connected to in-game wagering or chance outcomes — regulatory risk, worse given minors could plausibly access it. If monetisation is revisited later, the only acceptable pattern is flat-price cosmetic/commemorative items that are never linked to chance or convertible into in-game stakeable currency.
5. **Deployment target is a PWA** (installable website via Next.js/Vercel), not a native app store submission. Don't introduce native-only APIs or a native wrapper without an explicit decision to revisit this.

## Architecture

- `src/lib/sim/` — the race simulation core. Pure, React-free, fully typed. `expected()`/`runRace()` (race.ts), `makeHorse()`/`makeCandidateHorses()` (horse.ts), gear effects (gear.ts), `courses.ts` (course data + `TIER1_COURSES`/`TIER2_COURSES`), `yards.ts` (the single `YARD` trainer, Simon Bridges), plus `classStats.ts` (real-data OR/field-size distributions per class) and `roster.ts` (the persistent NPC horse pool — see "Historical data" below).
- `src/lib/game/` — the game state machine sitting on top of `lib/sim`. `engine.ts` holds `newGame`/`resolveHorsePick`/`advanceDay`/`resolveRaceDay`/`chooseDecision`/`enterRace`/`toggleGear` as pure functions over a typed `GameState`; `tracks.ts` holds `unlockedCourses()`/`REPUTATION_TIER2_UNLOCK`; `content.ts` holds ordinary day-content generators (`trainingMoment`, quiet-day/news lines); `story.ts`/`storyContent.ts` hold the entire scripted narrative — Act 1's nemesis arc, Act 2's Classics, Act 3's Diamond Cup/father subplot/ending (see "The scripted narrative" below); `storage.ts` is the localStorage save/load layer; `metrics.ts` holds the shared threshold-crossing/perception-overflow helpers; `quiz.ts`/`quizBank.ts` hold the quiz mechanic; `pressContent.ts` holds pre/post-race press beats; `pressRoom.ts` holds the player-initiated Press Room actions; `vetBills.ts` holds the injury vet-bill decision; `upgrades.ts` holds the one-time yard-upgrade catalog; `variety.ts` holds the shared flavour-pool "seen" cooldown (see "Money sinks..." and "Playtest feedback round 5" below for all of these).
- `src/components/` — the UI. `intro/` (`IntroScreen` — opening image only, no name entry; `HorsePickScreen` — single-select from the 6 candidates, see "Horse acquisition" below), `game/` (header, overlays — daily flash, decision, live race, help — tab bar, five tabs including `PressRoomTab`, advance bar, `EndingScreen` — career summary + share card), `ui/` (small primitives: Card, StatBar, PlanButton, Button).
- `src/app/page.tsx` — top-level orchestration: owns `GameState`, wires engine calls to UI callbacks, handles localStorage load/save.
- Styling: Tailwind v4 with custom `@theme` tokens in `src/app/globals.css` matching the original prototype's dark-purple-and-gold racing-diary palette (`ink-*`, `gold-*`, `parchment-*`). `font-diary` = Georgia serif (narrative text), `font-mono` = Courier New (UI chrome/numbers) — this mirrors real racecard typography conventions the prototype was built around.

## Tuned sim constants — validate before changing

The noise/spread constants below are calibrated against real outcomes from `ggs/races_master_v4.csv` (see "Historical data"), not hand-tuned by feel. If retuning, regenerate the grid-search rather than eyeballing it — the first attempt at this (the prototype's original 0.05-0.22 noise range) produced a 75% simulated favourite strike rate against a real 34.1%, which is exactly the kind of error that "feels roughly right" until you check it against data.

- **Race-day noise**: `noiseSd(h) = clamp(0.735 - (temperament/100)*0.315 + gearNoise, 0.26, 1.16)` (`lib/sim/race.ts`). This is the prototype's original formula scaled ×5.25 — that scale factor was grid-searched to match the real 34.1% favourite strike rate (n=2142 favourite-marked runners, tier-1 courses). Gear `noiseAdj` values in `lib/sim/gear.ts` are scaled by the same ×5.25 so gear's relative effect on consistency doesn't round to nothing.
- **Roster field-composition band width**: exact match on `Horse.rosterBand`, not OR-value proximity. An OR-window filter (even ±0.5 std) was tested and let neighbouring class bands' Gaussian tails bleed into each other, inflating a single race's effective rating spread — the calibration above assumes single-band fields, so the filter has to actually produce them.
- **Softmax temperature**: `3.2` in `runRace()`'s odds calculation — controls the displayed SP *spread* across the field, not who wins (win/lose is decided by the noisy `score`, and softmax is order-preserving, so the SP favourite and the noisy-score favourite are always the same horse). Not yet validated against the real odds-bucket calibration table pulled during analysis; lower priority than the win-rate fix since it's cosmetic.
- **Course-interaction weights** (`expected()` in `lib/sim/race.ts`): sharpness penalty ×0.035, undulation penalty ×0.03, finish-climb penalty ×0.04, break bonus ×0.06 (sprints ≤6f) / ×0.02 (longer), course mastery worth up to 5% (`×0.05`). Not recalibrated against real data yet.
- **Injury base rates**: gallop/sprints training = `0.02 + (fatigue/100)*0.05` per day (`engine.ts`); stalls-practice decision = 10%; "let it stretch out" decision = 12%.
- **Handicapper mark deltas** (`resolveRaceDay` in `engine.ts`): win by ≥2.5L → +6 to +9lb; any win → +3 to +6lb; close-up place (gap <1L) → +1 to +3lb; well-beaten (gap >4L) → -3 to -6lb; moderate effort (gap >2L) → -1 to -3lb.
- **Day-content roll** (`advanceDay`): 35% quiet flavour line, 15% news line, 30% decision event, 20% nothing — raised from the original 42/18/18/22 split per playtesting feedback that the early game felt too thin. Within that 30% decision bucket, ~30% is a quiz (`quizMoment()`) and the rest an ordinary `trainingMoment()`.

The constants below (round 5) are explicit judgement calls, not calibrated against `ggs/` data — noted here for consistency with the rest of this section, not because they carry the same validation weight as the noise/spread constants above.

- **Entry fee**: `entryFee(grade)` in `engine.ts`, `max(£15, round(PRIZE[grade][0] * 0.015 / 5) * 5)` — roughly £40 at Class 6 up to £4,500 at G1.
- **Vet bill**: `£35/day` of assigned `injuryDays`, halving the recovery time if paid (`vetBills.ts`).
- **Gear fitting cost**: `£40-90` per item, charged on every off→on toggle, not a one-off (`gear.ts`'s `GearItem.cost`).
- **Yard upgrade prices**: `£700 / £1,200 / £2,000` for physio / recovery / travelling team (`upgrades.ts`).
- **Race-experience grade cap** (`experienceCap()` in `race.ts`): 0-1 career runs → Class 5 max; 2-4 runs → Class 3 max; 5+ runs → uncapped.
- **Skill's result-scaled race-day gain** (`resolveRaceDay`): win 7, top-3 4.5, close defeat (<2L) 2.5, well-beaten 1 — all still run through the same diminishing-approach curve as everything else Skill-related.
- **Skill's daily training/walk rates**: active-training day `0.35 * (1-skill/100)` (was 1); course walk `1.3 * (1-skill/100)` (was 4).

## Historical data

`C:\Users\jackr\ggs` holds the user's own Betfair ML pipeline. The dataset actually used so far is `races_master_v4.csv` (real flat-racing results, 2022-2026, ~530k rows) — the dated `*racecard.csv` files and `betfair_2026_results.csv` are 2026-only and weren't needed for this pass. This is the *only* permitted source of real racing data (see hard rule 3); only aggregate numbers (mean/std of OR and field size per class) were pulled out, never real horse/trainer/jockey names or comment text.

**What's wired in**: `lib/sim/classStats.ts` holds real per-class OR mean/std and field-size mean/std (tier-1 courses: Newmarket, Goodwood, Sandown, Epsom Downs — "Class" in British racing is a national ability band, not course-specific, so this generalizes to races at any course). `lib/sim/roster.ts` uses it to seed a ~120-horse persistent NPC pool (`GameState.roster`, created once per new game in `newGame()`) instead of inventing a throwaway field from scratch every race — this is what makes rival horses recur across a season with an evolving win/run record, and it's what the noise calibration above was validated against. `G3`/`G1` bands in `classStats.ts` are informed extrapolation (the dataset lumps all Group/Listed races into one "Class 1"), flagged inline for future recalibration if a Pattern-race-only sample becomes available.

**Not yet done**: applying this same real-data approach to non-flat/other calendar specifics, and recalibrating the softmax temperature and course-interaction weights the same rigorous way (both currently just carried over from the prototype).

## Single trainer + track tiers

The original 3-boss/yard picker is gone — `lib/sim/yards.ts` exports one `YARD` constant: Simon Bridges, Newmarket, built around the backstory in the Act 1 opening (he trained alongside Tony's grandfather; Tony's father gambled the family name away). The previous passes' placeholder personas (Marina Delacroix-Hale, Frank Berrow, Sonny Okafor) weren't deleted — they're folded into `RIVAL_TRAINERS` in `lib/sim/race.ts` so their writing still surfaces in race results instead of being wasted. Martin McLean is deliberately **not** in that pool — he's a persistent nemesis tied to one specific horse; see "Act 1 scripted narrative" below.

Courses are split in `lib/sim/courses.ts`: `TIER1_COURSES` (Newmarket, Epsom, Sandown, Goodwood) are open from game start; `TIER2_COURSES` (Ascot, Doncaster, York, Chester — Doncaster specifically so the St Leger is something to build to) unlock once Reputation clears `REPUTATION_TIER2_UNLOCK` (35, in `engine.ts`). `unlockedCourses(reputation)` is the single source of truth for what's open — used by `makeSlate()`'s course pool and by `NotebookTab`'s lock-gating. There's no more "your yard's home tracks" concept; the player starts with a little course mastery at all four tier-1 tracks instead of two.

## The four metrics

Two families, deliberately separated: three "who's judging you" axes (perception) and one "what you actually have" axis (capability). This is the user's own design spec (verbatim reasoning kept here since it explains *why* each rule exists, not just what it does) — implemented in `resolveRaceDay`/`advanceDay` in `engine.ts`, surfaced in `YardTab` and the header.

1. **TRUST** — one person's private opinion of you (the boss specifically, not the wider world). Can go down. Critically, it's movable by things that aren't race results (the targets-vs-process conversation, the press-quote choice indirectly, etc.) — that's what keeps it from feeling redundant with Reputation. Gates: second horse, trade-up offers, entry to bigger races. Unchanged from the original prototype.
2. **REPUTATION** — what insiders (jockeys, other trainers, owners, the handicapper) think of your ability. Lagging, results-driven, grade-weighted (`gradeWeight()` in `engine.ts`: a G1 win is worth 18, a Class 6 win is worth 1). Can go down on a bad-beat run. Gates tier-2 track access. *New this pass* — the design was described in earlier project notes but had never actually been built; don't assume it existed before this.
3. **CELEBRITY** — public/media profile, distinct from insider respect. Deliberately pulls *against* Reputation: the new "local paper wants a word" `trainingMoment` event (`content.ts`) is a genuine trade-off (big quote: +celebrity, -reputation; modest quote: +reputation only), not a free top-up. Big-race wins (G1/G2) also bump it a little ("hyped horses"). **Not yet wired into the sim**: the spec calls for Celebrity to nudge a horse's market SP shorter independent of true ability (public sentiment moves markets in real racing, creating a "smart money vs public money" dynamic) — deliberately deferred rather than bolted on same-session, since it touches the `runRace()`/softmax odds math that was just carefully calibrated against real data (see "Tuned sim constants"); redo the grid-search validation if this gets built.
4. **SKILL** — the trainer's own accumulated capability. Never falls — framed as an XP bar, not a score, specifically to give a losing streak something that still goes up. Caps at 100, stored at 1-decimal precision, rounded only at display (`Header.tsx` needs an explicit `Math.round()`, unlike `StatBar` which already rounds internally). Growth is a diminishing-approach curve (`skill = skill + N * (1 - skill/100)`), not a flat rate — per playtesting feedback (round 4) that a flat rate just abruptly froze at the 100 cap instead of visibly slowing down; see "Training ceilings" below for the parallel change to horse stats. Scales training effectiveness up to +30% (`skillMult` in `advanceDay`) — this is literally the same hidden `trainMod`-style constant the original spec calls out, just surfaced as a real, player-visible stat instead of staying buried. **Round 5 rework**: growth is now primarily *results*-driven, not *time*-driven — a round-5 playtest report showed Skill reaching "Elite" (60+) after only 40 days with zero race wins, purely from daily training/course-walk volume. `resolveRaceDay()` now applies a result-scaled base gain right after `mine`'s finishing position is known (win 7, top-3 4.5, close defeat <2L 2.5, well-beaten 1 — always non-zero, "racing teaches you something regardless of result" is kept, just no longer flat) plus one-time milestone bonuses (`bumpSkill()`: first win +8, Listed win +6, Group win +8, Group 1 win +12, each gated on the milestone flag newly flipping true). The old flat per-day contributions were cut hard rather than removed outright — active-training days now add `0.35 * (1-skill/100)` (was 1) and a course walk adds `1.3 * (1-skill/100)` (was 4) — training/study still matters, it just isn't the dominant driver any more. Verified via a 46-training-day-only scripted run: Skill now sits at ~11 ("Unproven") at the point it previously hit 62 ("Elite"). Further gates (faster hidden-trait reveals, spotting a well-handicapped horse before the market) are designed but not built.

**Metric overflow (Trust/Reputation/Celebrity only)**: gains that would push a perception metric past 100 spill 50% into the *other two* perception metrics instead of being lost outright (`applyPerceptionOverflow()` in `metrics.ts`) — "you can't get more famous than famous, but the attention doesn't go nowhere." Deliberately scoped to `resolveRaceDay()`'s race-day deltas only (ordinary races, Classics, the Diamond Cup) — **not** migrated into every individual decision's small delta across `content.ts`/`storyContent.ts` (40+ call sites for comparatively tiny amounts, not worth it). `resolveRaceDay()` leaves `trust`/`reputation`/`celebrity` unclamped through its outcome branches and applies the overflow once at the end — the Diamond Cup's `computeEnding()` call was moved to *after* that step specifically, since deciding the ending on since-corrected numbers would be wrong.

**Threshold-unlock system**: crossing a new 5-point band on any of the four metrics (`floor(new/5) > floor(old/5)`) fires a small, generic cash reward + acknowledgment (`checkThresholds()` in `metrics.ts`) — not bespoke content per threshold (4 metrics × ~20 bands is too much to author). Detected in exactly two places — `chooseDecision()` and `resolveRaceDay()` — since between them they cover effectively every way these metrics change, without needing to touch individual `apply()` functions. **Important**: `resolveRaceDay()` itself does *not* run this check, even though it changes these metrics — it's always invoked through a "Riding instructions" decision, so `chooseDecision()`'s wrapper already catches every race-day crossing too; checking it twice doubled both the message and the cash reward (caught via a long scripted playthrough, not tsc/lint — see "Bug classes" below).

**Playtesting note, resolved**: a synthetic auto-play bot (train one stat only, always accept the first offered race, always pick the first decision option) went 0-for-33 over one test run, and this 0-for-many pattern reproduced again in a later 900-day scripted run. Originally chalked up to "a naive strategy against a deliberately weak starting horse" — that was the wrong explanation. The real cause, found via a round-3 playtest report (a Class 6 declared race showing rival marks in the 80s-90s against the player's own ~40-something), was a genuine bug in `lib/sim/roster.ts`'s `makeRoster()`: it built the roster by iterating `Object.keys(CLASS_STATS)`, and `Object.keys()` always returns strings even for numeric keys — so every roster horse in the numeric bands (Class 3/4/5/6) got `rosterBand = "6"` (a string) instead of `6` (a number), despite the `as (keyof typeof CLASS_STATS)[]` cast, which is compile-time-only and doesn't change the runtime value. `eligibleForGrade()`'s `h.rosterBand === grade` strict comparison then never matched any numeric-graded ordinary race (`race.grade` from `makeSlate()` is a genuine number), so `drawField()`'s neighbour-widening fallback silently walked out to the Listed band (a real string key, "L", which matched correctly) for **every** Class 3-6 race — i.e. nearly all early-game races — pitting a fresh horse against opposition rated ~90 instead of the correct ~55-77 for that class. Fixed by iterating `BAND_ORDER` (already correctly typed) instead of `Object.keys(CLASS_STATS)`; verified a Class 6 race now draws a field averaging mark ~58, matching the real Class 6 mean (57.7) from "Tuned sim constants" below. This was likely the actual driver of the repeated 0-for-many pattern, not the starting horse's rating — re-run the naive-bot test if validating this further.

**"Reveal after, not before" (per playtesting feedback)**: `Choice.hint` on any decision that moves Trust/Reputation/Celebrity/Skill is deliberately omitted — the player commits to a choice without seeing its metric impact in advance, then the impact is revealed as an explicit `(Metric ±N.)` suffix appended to the post-choice narrative text (`note()`'s text argument). This applies across `content.ts` and `storyContent.ts`. It does **not** apply to `hint`s describing a mechanical/training choice (which stat a horse trains, which track gets studied, physical +stat/+fatigue effects) — those aren't "moral choice" reveals, they're the entire visible point of a resource-allocation decision, and stay visible before the choice (e.g. `BEAT7_BRIDGES_ADVICE`, `makeBeat8AllyTrainer`).

## The scripted narrative (Tony Vincenzo, Simon Bridges, Martin McLean)

This is the fix for the "biggest known design gap" flagged early on — real branching narrative and a persistent rival, not just ambient random content. The whole arc (Act 1 nemesis intro → Act 2 Classics → Act 3 Diamond Cup/father subplot → ending) was planned and built across two passes; this section is the load-bearing summary for future changes, not a duplicate of the approved plans (`~/.claude/plans/replicated-sleeping-sedgewick.md` has the original scoping detail if ever needed, but treat this section as authoritative over that file, which isn't updated after the fact).

### Act 1: the opening + the nemesis

**Flow**: `IntroScreen` (opening image, no input) → `newGame()` seeds `GameState.queue` with beat 2 (Bridges' office) → beat 2 enqueues beat 2b (Ray Fenwick, the head lad — pure characterisation, added because the jump straight from office to horse pick felt too rushed in playtesting) → beat 2b enqueues beat 3 (yard scene with jockey Rossa Bellini) → beat 3 sets `awaitingHorsePick`, which `page.tsx` renders as `HorsePickScreen` (single-select from the 6 `horseCandidates` `newGame()` generated — see "Horse acquisition" below) → `resolveHorsePick()` schedules the nemesis intro and normal play begins. `GameState.story.stage === "yard"` is what tells `page.tsx` to render the minimal pre-game chrome instead of the tabbed shell; everything from `"preNemesis"` onward fires through the ordinary `DecisionOverlay`/`DailyFlashOverlay`, same as any other content.

**Beats 2/2b/3 are single-choice (`choices: [{ label: "Continue →", ... }]`), not real decisions.** They originally had 2-choice branches (a consequence-free "grandfather or father?" line for beat 2, a flavour-only question for 2b, and a real reputation/celebrity-affecting response for beat 3) — per playtesting feedback that these opening "decisions" read as fake interaction rather than meaningful ones, they were rewritten as narrated scenes the player just clicks through, same as `DailyFlashOverlay`'s `CONTINUE`. Beat 3's stat deltas were dropped entirely rather than arbitrarily picked, embracing "not a real choice" fully instead of half-measuring it. This reuses `DecisionOverlay`/`chooseDecision` completely unchanged — a `DecisionEvent` with one choice just renders one button instead of two, no new component needed. Don't assume every early beat needs branching choices to feel like content; scene-setting narration between real decisions (the McLean arc, the four-metric choices, etc.) is fine.

**The nemesis (Martin McLean, McLean Racing, Middleham)**: a rival *trainer*, not jockey — deliberately given his own persistent mount (`story.nemesisHorseId`, added to `GameState.roster` when he's introduced, always tagged `trainerName: "Martin McLean"` via `ensureNemesisInField()` in `story.ts` rather than the normal randomized trainer-name assignment other roster horses get). Introduced ~4-6 days after the horse pick (`scheduleNemesisIntro()`: `day + ri(3, 5)`, beat 4, flash-only) — deliberately early, per playtesting feedback that the hook needed to land sooner (previously ~7-10 days). His mount is then **forced** into the player's next declared race — `story.forceNemesisNextRace` — with a pre-race reporter decision (beat 5) and a **guaranteed loss**: `forcePosition()` in `story.ts` swaps scores after `runRace()` computes a normal result, so the scripted defeat still looks like a physically coherent race, not an obviously fake one. Beat 6 (McLean's taunt) follows immediately. A second meeting fires ~110-130 days later (beat 9) — McLean is forced into the field again the same way, but this time the outcome is genuinely probabilistic (verified: both a player win and a nemesis win occur across repeated test runs). `story.headToHead` tracks the record across both. Beats 7 (Bridges advice — pick a stat, all horses improve) and 8 (ally trainer Callum Rees — pick a track, big mastery jump) fire in between on their own day-triggers.

**Horse acquisition**: the player starts with exactly **one** horse (single-select `HorsePickScreen`, not the original 3-of-6), and grows the string on race results rather than Trust — per playtesting feedback that the original 3-horse start made the first choices feel inconsequential. In `resolveRaceDay()` (applies uniformly to ordinary races, Classics, and the Diamond Cup — not gated to any one race type): a top-3 finish (`mine.pos <= 3`) grants a second horse (`milestones.secondHorse`); once total wins across the whole string (`horses.reduce((sum,h)=>sum+h.wins,0)`) reaches 3, a third horse is granted (`milestones.thirdHorse`). The old trust≥45-gated second-horse trigger in `advanceDay` was removed; the separate trust≥75 trade-*offer* mechanic (swap a horse for a better one) is unrelated and unchanged.

### Act 2: the Classics

Once Act 1 reaches `story.stage === "ongoing"` **and `GameState.year >= 2`** (see "Multi-race declarations..." below for why this gate exists and how it's enforced), the Classics run on their **own independent CALENDAR-day schedule** — the two arcs deliberately overlap in real time (McLean's second meeting can land mid-Classics) rather than waiting on each other. `CALENDAR` in `lib/sim/calendar.ts` holds the five real Classics (see hard rule 1's exception); each one's own mini-arc lives in `story.ts`/`storyContent.ts`: a dynamic horse-choice decision (`story.classicArc`, ~20-40 days out depending on which Classic), McLean entering + media doubts folded into one decision, an automatic top-jockey booking (a temporary `jkSkill` boost tied to `race.isClassic`, not tracked as separate state — "eventually the top jockey takes the horse" is treated as inevitable), the race itself fully probabilistic, then a **four-way outcome branch** (win/place/okay/tank) via `classifyClassicOutcome()`/`resolveClassicOutcome()`, with **diminishing-returns-scaled** deltas (`CLASSIC_DIMINISH = [1, 0.7, 0.5, 0.35, 0.25]` across the five). Results accumulate in `story.classicResults`, which an occasional press-callback (`makeClassicCallback`, folded into the ordinary `trainingMoment` pool) can reference later.

**Balance bug caught via testing**: tagging all five Classics grade `"G1"` for real-world authenticity meant every one drew opponents from the real-data G1 band (mean rating ~108) regardless of each Classic's own `minOR` (76-94) — every test run came back "tank". `grade` in `CALENDAR` is a gameplay dial selecting the opponent-strength band (see `roster.ts`), not a strict real-world label — it now escalates L/G3/G2/G1/G1 across the five, matching the original (pre-Classics-rename) calendar's validated balance, while keeping the real race *names*.

### Act 3: the Diamond Cup, the father subplot, the ending

Begins once `story.classicIndex` reaches 5 (all Classics resolved) — scheduled on **relative** "days since the previous beat" (`story.diamondCup.nextBeatDay`/`raceDay`), not fixed calendar days, since it's scripted-only with no `CALENDAR` entry backing it. Sequence: announcement (a fictional one-off prize, deliberately bigger than the Breeders' Cup, `DIAMOND_CUP_PRIZE` — completely outside the normal `PRIZE` table) → McLean entering → the father subplot (Michael Vincenzo backs McLean for a paid-off quote, then a confrontation scene — accept the apology vs air it in the press, real trust/celebrity trade-off) → horse choice → an injury scare that resolves as a false alarm (flavour only, never touches `injuryDays`) → the race itself, biggest deltas in the game (`resolveDiamondCupOutcome()`), no diminishing returns since it only happens once.

Once the Diamond Cup resolves, `computeEnding()` evaluates the final Trust/Reputation/Celebrity: Trust ≥60 → contract extension (`"contract"`); else Reputation or Celebrity ≥50 → poached by a rival trainer (`"poached"`, deliberately reuses Marina Delacroix-Hale rather than inventing a new name); else released (`"released"`). `page.tsx` renders `EndingScreen` once `GameState.ending` is set (gated on `!g.liveRace` so the Diamond Cup's own commentary plays out first) — a career summary (final four metrics, Classics list, Diamond Cup result, McLean head-to-head, horses' records) plus a client-only share card (`navigator.share` with a clipboard-copy fallback — no backend, per explicit user choice; there isn't one for this project yet).

### The live race visual track (per playtesting feedback: "the race itself needs to be the exciting bit")

`LiveRaceOverlay.tsx` previously showed nothing but text (`liveRace.beats[liveRace.idx]`, the 12-entry `string[]` from `makeBeats()`). It now also renders a small visual track above the text: one fixed lane per runner, a numbered/silk-coloured circular icon per lane sliding from the stalls (left) to the finish line (right) as the player steps through `liveRace.idx`, plus a compact key (colour swatch + number + name, player's horse called out in gold) above the track. The stepping mechanic itself (`▶` / `THE FINISH →` / `BACK TO THE YARD`, `page.tsx`'s `onNext`) is unchanged.

`runRace()` (`lib/sim/race.ts`) is a single-shot Monte Carlo — it has no real notion of "at furlong 6, horse X is in 3rd" for the whole field, only final scores/positions. Rather than touch that calibrated math (see "Tuned sim constants" — not to be perturbed for a cosmetic feature), the per-beat per-runner position is a **fabricated, deterministic, post-hoc interpolation**, computed once at race resolution: `computeRaceTrack(res, mine, tactic)` in `lib/sim/commentary.ts`, called alongside `makeBeats()` in `resolveRaceDay()` and stored on `GameState.liveRace.track` (not recomputed on re-render, so the animation doesn't jitter). **Round 5 rework — see "Playtest feedback round 5" below for the full story**: `makeBeats()` and `computeRaceTrack()` used to each compute their own independent interpolation and could disagree; they now both read from one shared `computeFieldRanks(res, tactic)` table (a per-runner, per-beat ordinal rank, generalizing the old player-only `posAt()` trick to the whole field — rivals get a deterministic "early pace" rank derived from their own `brk` stat rather than random noise). Lane order used to be `sort by horse.id`, which put the player's horse in lane 1 almost every race (its id is always low — created before the ~120-horse roster); lanes are now a real per-race shuffle, and each runner also carries its real `pos` so the UI can show a guaranteed "FINISHED Nth of N" placard once the final beat plays (`LiveRaceOverlay.tsx`).

Also added in the same pass: several previously-static `makeBeats()` lines (the early-pace description, "makes a move on the outside," "the crowd starts to roar," etc.) now pick from 2-3 phrasing variants each, same `pick()`-pool pattern already used by `CMT_WIN`/`CMT_PLACE`/`CMT_ALSO`, so replaying races doesn't read identically every time.

### Daily morning report + UI variety (per playtesting feedback)

`advanceDay()` builds a `reportLines: string[]` array — per-horse training-type and the resulting primary stat value (or injury-recovery status), a course-walk summary, a skill-increase line, and a new-race-slate line — concatenated with the day's ordinary messages/news into `flash: string[] | null`. This is **always** attached when non-empty (`flash: flashLines.length ? flashLines : null`), including on a day that also queues a decision: `DecisionOverlay` (z-31) renders over `DailyFlashOverlay` (z-30), so the report surfaces automatically right after the decision is dismissed rather than being dropped. Before this pass the flash was gated on `queue.length === 0`, silently discarding a fully-computed report on any day a `trainingMoment` decision also fired (~30% of days) — caught via a scripted-playthrough run showing ~14% of days with no flash at all.

`DecisionEvent.tag?: DecisionTag` (`"PRESS" | "BOSS" | "RIVAL" | "TRAINING" | "FAMILY" | "YARD"`) is a purely cosmetic category label — `DecisionOverlay` uses it to pick a border/pill accent colour (`TAG_COLOR` map) so decisions don't all render identically, per feedback that the UI felt "very samey." Every `DecisionEvent`/factory in `content.ts` and `storyContent.ts` is tagged; it has no effect on game logic.

### Multi-race declarations, rival visibility, and metric glanceability (round 2 playtesting feedback)

A second real playtest ("a few weeks" of game-days) surfaced a core "grind" complaint traced to two causes, both fixed together:

- **`GameState.entered` was a single slot for the whole yard.** Declaring one horse into a Classic (scripted weeks ahead) blocked every other horse from racing until that one race day arrived. `entered` is now `EnteredRace[]` — one entry per horse, not one for the whole yard. `enterRace()` pushes onto the array (also computing that entry's `fieldPreview`, see below) instead of overwriting, and only removes the just-declared race from `slate` rather than clearing the whole thing. `advanceDay()`'s going-change and race-day checks loop over all due entries instead of early-returning on the first (and only) one — a horse whose race lands today no longer blocks the rest of the string's training/report that day. `resolveRaceDay(st, tactic, raceId)` takes an explicit race id now, resolving just that one entry. `RacingTab.tsx` renders one Declared card per entry, alongside the slate (not either/or), with each button filtering out horses already entered elsewhere.
- **The Classics ran in year 1**, almost immediately after the single-horse start — no time for the results-based string-building above to matter before the biggest scripted races arrived. They're now gated to `year >= 2` in `story.ts`'s `checkStoryTriggers()`. Because `day` is day-of-year (resets every year) and nothing previously checked `year` anywhere in the trigger/race-day logic, this **had** to be an explicit year check — retuning `CALENDAR`'s `day` values would not have worked, since year 1 day 50 and year 2 day 50 are indistinguishable to a day-only comparison. `RacingTab.tsx`'s big-race calendar tab has its **own separate manual-declare path** into a Classic (bypassing the scripted horse-choice arc entirely) that needed its own identical year gate, or the year-2 requirement could just be sidestepped by declaring from that tab instead.
- **Eligibility filtering for the Classic/Diamond Cup horse-choice trigger must only exclude real scheduling conflicts, not "has any entry at all."** An early version of the year-2 fix excluded any horse with *any* pending entry from Classic eligibility — since ordinary bookings almost always resolve weeks before a Classic's own fixed date, an active player who keeps every horse booked into near-term races (exactly what multi-race declarations are meant to encourage) could starve the trigger indefinitely. Fixed by only excluding a horse if its existing entry's `raceDay` is within ~10 days of the Classic's own `raceDay` — see bug class 4 below.
- **Rival field preview**: each declared race gets a one-off, indicative `fieldPreview` (name/trainer/mark for the likely opposition), computed once at declare time via the same `drawField()` roster machinery races already use (`engine.ts`'s `enterRace()`, plus the same logic duplicated in `storyContent.ts`'s `makeClassicHorseChoice`/`makeDiamondCupHorseChoice` since those also create entries directly). It's deliberately *not* the exact field `resolveRaceDay` later draws — reusing/locking a field would also need to replicate the McLean forced-insertion timing, real complexity for a "just show me the competition" UI want. Results also now show every finisher, not just the top 6 (`resolveRaceDay` no longer slices `res` before storing it).
- **Header now shows all four metrics with a cosmetic rank label** (`lib/game/ranks.ts`'s `metricRank()`: Unproven/Rising/Established/Elite/Legend at 0/20/40/60/80) — previously only Trust/Reputation were in the header at all, Celebrity/Skill were YardTab-only. This is the direct answer to "what happens at 100": the metric still hard-caps, the rank name is what communicates that the cap means something. A genuine next step the user raised — trading further gains from an already-maxed metric into the others — is **not built**: it would need every inline `clamp(st.X + n, 0, 100)` call site across `content.ts`/`storyContent.ts`/`engine.ts` migrated to a shared helper that can detect and redirect overflow, a large, separable refactor left for its own pass.
- **`resolveRaceDay()` now states its own Trust/Reputation/Celebrity deltas** as an explicit message (`Trust +N, Reputation +N, Celebrity +N.`, only pushed when at least one actually changed) — previously only decision outcomes got this "reveal after" treatment; race-day changes happened silently.
- **Decision-outcome toast**: the reveal-after delta text has always existed (`note()`'s message), but was only ever visible by manually opening the Yard tab's message log — no immediate on-screen confirmation after choosing. `page.tsx` now captures the just-resolved decision's outcome message into local (non-`GameState`) UI state and shows it as a dismissable banner at `z-[35]` — above `DecisionOverlay` (z-31) and `DailyFlashOverlay` (z-30) — so it's the first thing shown, then dismissing it reveals whatever's queued next. Deliberately not wired into the pre-horse-pick intro screens (`story.stage === "yard"`), since no metrics are visible there yet.

### Training ceilings, the quiz mechanic, more press content, and the Press Room (round 4)

A single large playtesting-feedback message covering several requests at once — kept together here since they shipped in the same pass, but each is independent.

- **Per-horse training ceilings**: `Horse.statCeilings` (`{ speed, stamina, accel, brk, balance }`, `lib/sim/types.ts`) — a randomized headroom generated once in `makeHorse()` (`clamp(current + ri(10, 30), current, 99)` per stat), patched upward if `makeCandidateHorses()`'s quirk bonus would otherwise push a stat past its own rolled ceiling. `advanceDay()`'s training gain formula targets `h.statCeilings[k]` instead of a universal 99 — every horse can still improve a lot, but not converge to the same elite ceiling regardless of starting quality, which was the actual complaint ("otherwise someone just has loads of full-stat horses"). Not shown as a raw number to the player (same "hidden until discovered" spirit as `prefGoing`/`prefDist`) — when an actively-trained stat lands within ~2 points of its ceiling, the daily report line swaps to a "seems to be reaching full potential" flavour line instead of the normal "speed now X" one.
- **New training option, `"sharp"`**: gentler than the five focused types (`gallop`/`canter`/`sprints`/`stalls`/`school`) — small gains spread across *all five* stats at once instead of one stat hard, modest fitness gain, low fatigue cost, no injury-risk roll (unlike gallop/sprints). The natural choice once a horse is nearing its ceiling, or just for upkeep. Counts toward `ACTIVE_TRAINING` for Skill-gain purposes.
- **Quiz mechanic** (`lib/game/quiz.ts` + `quizBank.ts`): the originally-deferred track-knowledge quiz and a new stat-boosting general-trivia layer, sharing one ~50-question bank and one `quizMoment()` generator (fired from the same day-content roll `trainingMoment()` already uses, ~30% of decision-days). `category: "track"` questions draw on the course facts already written in `courses.ts` and reward mastery for that question's own course; `category: "general"` questions (terminology, distances, rules, real *race* names — an established exception, see hard rule 1 — deliberately **not** real jockeys'/trainers' names, since that rule's spirit plausibly extends to trivia even though it isn't roleplay) reward a modest stat boost on a random fit horse. Wrong answers aren't penalised, just requeued via `GameState.quizMissed` with `dueAfter = quizCount + 3` — "3 questions' time" means 3 quiz *occurrences*, not calendar days. Difficulty pool shifts harder as `quizCount` grows (simple threshold bands, not a smooth curve). New `QUIZ` `DecisionTag`.
- **More press content, lighter tone**: `content.ts`'s `trainingMoment` pool grew from 9 to 17 templates with an explicit humour pass (the yard cat, a betting "system" involving moon phases, a sausage-sponsorship offer) — deliberately more comic than the scripted narrative beats, which is fine since it's ambient colour, not the main story. New `lib/game/pressContent.ts`: generic, parameterised (not one-off per race) pre-race press (`makePreRacePress`, ~40% chance, prepended before the "Riding instructions" decision) and post-race press (`makePostRacePress`, ~35% chance, win/loss-aware) for *ordinary* races — the scripted McLean arc and the Classics/Diamond Cup already have their own dedicated reaction content, so both are skipped for `e.isClassic`/`e.isDiamondCup`.
- **Press Room** (`components/game/PressRoomTab.tsx` + `lib/game/pressRoom.ts`): a 5th tab, player-*initiated* actions rather than random events. Four actions (talk up a horse, give a measured interview, pick a fight with a rival trainer, court the press for a feature), each usable once per day (`GameState.pressRoomUsed`, reset every `advanceDay()`) — outcomes surface through the same `outcomeText` toast `page.tsx` already uses for `DecisionOverlay`, just triggered from a direct button click instead. "Pick a fight" has a ~35% chance of scheduling a rival-comeback beat (`GameState.pressRoomFollowupDay`, checked in `advanceDay()` the same way other day-triggers already are — plain day-number data, not a stored closure, since state has to survive `JSON.stringify` for localStorage).
- **New-horse acquisition is now an unmissable moment**: earning a second/third horse used to be one line in `resolveRaceDay()`'s message stack — easy to miss if other messages were generated the same race. `makeNewHorseAnnouncement()` (`storyContent.ts`) builds a proper single-choice "Continue →" `DecisionEvent`, same pattern as the rewritten intro beats, queued via `queueExtra` so it gets its own full-screen moment.

### Money sinks, race realism, and pacing fixes (round 5)

A structured playtest report (46 days / 6 races, zero wins) covering eight distinct issues. Several turned out to share a root cause; grouped here by that, not by the report's own numbering.

- **Money had no purpose at all**: not even the entry fee the withdrawal flavour text already implied ("Costs us the entry fee, mind"). Four sinks, all judgement calls, none touching the calibrated race-sim math: **entry fees** (`entryFee()` in `engine.ts`, ~1.5% of the grade's 1st-place `PRIZE`, rounded to the nearest £5, deducted in `enterRace()`, non-refundable on withdrawal); **vet bills** (`lib/game/vetBills.ts`'s `makeVetBillDecision()` — a real choice queued every time a horse picks up a training injury, £35/day, pay to roughly halve the recovery time or heal free on the full timeline); **gear fitting costs** (`GearItem.cost` in `lib/sim/gear.ts`, £40-90 per item, charged in `engine.ts`'s new `toggleGear()` every time a piece of kit goes from off to on — deliberately a re-fitting cost, not a one-off purchase, so there's no new persistent "owned gear" field to add); **yard upgrades** (`lib/game/upgrades.ts`'s `YARD_UPGRADES` catalog — three one-time purchases, £700-2000, `GameState.yardUpgrades: Record<string, boolean>` — on-call physio cuts vet bills 40%, a better recovery regime cuts injury duration 25%, a bigger travelling team adds +10% cash from every race's prize money — surfaced in a new card on `YardTab`). Cash is deliberately allowed to go negative — no floor — since a floor would just make the new sinks free once you're already broke, undermining the whole point.
- **The stall draw was never actually random**: `computeRaceTrack()` laned runners by sorting on `horse.id` ascending. The player's horse is always created early in `newGame()` (low id) relative to the ~120-horse roster (`makeRoster()`, high ids), so it landed in lane 1 essentially every race — not a bug that ever throws, so nothing caught it until a playtester noticed the pattern directly. Fixed by a genuine per-race Fisher-Yates shuffle of lane order in `computeRaceTrack()`; each `RaceTrackRunner.number` is now a real racecard-style draw, not a re-labelled id-sort index.
- **Commentary and the visual could disagree about where a horse was mid-race** ("broke sharply and sat mid-division" next to a visual showing dead last from the start): `makeBeats()` and `computeRaceTrack()` each had their own independent interpolation — `makeBeats()` tracked only the player's own rank via a tactic-based `posAt()`, `computeRaceTrack()` tracked no rank at all, just a final X-position plus per-runner random wobble uncorrelated with anything. Unified onto one shared table, `computeFieldRanks(res, tactic)` in `lib/sim/commentary.ts` — an ordinal rank (1 = leading) per runner per beat, generalizing the old player-only trick to the whole field (rivals get a deterministic "early pace" start rank from their own `brk` stat, not random noise, so it's replay-safe and loosely grounded in the same stat the break-line text already reads from). `makeBeats()` now reads the player's rank straight from this table instead of recomputing it; `computeRaceTrack()` derives each runner's X-progress as the field's nominal beat progress plus a small rank-based offset (ahead of nominal if well-placed, behind if not, zero at the stalls and the line) — the same number now drives both, so they can't contradict each other by construction, not by convention.
- **No feedback after a bad run**: `diagnoseRun(h, race, res, mine)` in `lib/sim/race.ts` — a rule-based, best-effort "why," reading the same sub-factors `expected()` already multiplies together (going/distance fit, course-balance interaction, stamina-vs-climb, fatigue, fitness shortfall, a class-strength gap against the field average) without touching `expected()` itself. Each factor is compared against its own "is this actually notable" baseline and the single largest surviving one wins, picked over trying to explain every factor at once. Only fires outside the top 3 with a real beaten margin (`mine.gap >= 1.5`) — a close-up defeat doesn't need an excuse — appended as a guaranteed `"Notebook: …"` message in `resolveRaceDay()`'s ordinary-race branch (the Classics/Diamond Cup already narrate their own outcomes).
- **"OR" and "mark" read as pointless duplication**: they're not — `OR(h)` is a live, stats-derived *true-ability* estimate that moves the instant training does; `h.mark` is the *official* rating, which only the handicapper's post-race review actually moves (see `resolveRaceDay()`'s handicapper-letter block, unchanged). The confusion was purely naming: real racing's own "OR" **is** the official/handicap rating, i.e. what this game calls `mark` — so labelling the live estimate "OR" in the UI was actively backwards terminology, not just an unclear pair. Fixed by relabelling in `StableTab.tsx` only (`TRUE {OR(h)} · OFFICIAL {h.mark}`, plus a one-line always-visible caption explaining the difference) — no functions renamed, no mechanic removed, since the underlying "well handicapped / a touch exposed" system is a deliberate, real-racing-accurate design already documented in `horse.ts`.
- **Flavour events repeated too often** (a 3-variant pre-race press pool, a 16-17-template `trainingMoment` pool, no de-dup anywhere): `lib/game/variety.ts`'s `pickFresh()`/`recordSeen()` — a generic, pool-size-agnostic cooldown. Excludes anything in a rolling `recent: string[]` history; once that would leave nothing to pick from, the pool has been fully cycled and starts fresh, so small 2-3-item pools still get real variety instead of either repeating immediately or being pinned to an arbitrary multi-day lockout that dwarfs the pool. `DecisionEvent` gained an optional `id?: string` purely for this tracking; `GameState.eventHistory: Record<string, string[]>` holds the per-category recent-id lists (`"training"`, `"preRacePress"`, `"postRacePressWin"`, `"postRacePressLoss"`), reset to `{}` on `newGame()`, threaded through `advanceDay()`/`resolveRaceDay()` alongside the events they gate.
- **Race difficulty was front-loaded, and an earlier fix hadn't addressed the actual cause**: the round-3 roster-band bug fix (bug class 5 below) only ever corrected *who you race against within a class* — it never touched *which class gets offered in the first place*. `makeSlate()`'s grade thresholds respond only to the player's horse's current raw OR, with zero regard for how many races it's actually run; a well-picked or lucky-quirked starting horse's OR can already sit past the Class 3/4 threshold on day one, before a single race. Fixed with `experienceCap()` in `lib/sim/race.ts`: 0-1 career runs caps the offered grade at Class 5 (never above, regardless of OR); 2-4 runs caps at Class 3; 5+ runs removes the cap entirely and the existing OR-based logic applies unmodified. `makeSlate()` gained a `runs` parameter (its one call site in `advanceDay()` passes `myBest.runs`).
- **Skill growth was time-driven, not results-driven** — see "The four metrics" above for the full rework (result-scaled race-day gain, one-time milestone bonuses, sharply cut daily training/walk rates).

### Bug classes worth remembering (caught by scripted-playthrough testing or manual browser verification, not `tsc`/lint/build)

1. **Uncleared day-triggers re-fire infinitely.** `advanceDay` doesn't increment `day` on a tick that queues a scripted beat, so any day-gated trigger (`story.bridgesAdviceDay`, `allyTrainerDay`, etc.) must null out its own trigger field the moment it fires, or it re-queues the same beat forever the next time `advanceDay` runs.
2. **A scripted race can be scratched.** If the horse declared for a Classic or the Diamond Cup gets injured before race day, the ordinary scratch path (`advanceDay`'s race-day check) just cleared `entered` and moved on — but nothing else ever resumed that arc, permanently stalling Act 2/3 (`classicArc`/`diamondCup` stuck mid-stage forever, `story.classicIndex` never reaching 5). Fixed via `skipClassic()` (a scratched Classic is a missed calendar date in real life — no stat penalty, just move to the next one, recorded as a `"scratched"` `ClassicOutcome`) and `rescheduleDiamondCup()` (no fixed calendar date, so just try again ~15 days later). Any new day-gated or scripted-declaration content should be tested against "what if the chosen horse gets injured mid-arc" specifically.
3. **A per-day computed result silently discarded by an unrelated condition.** The morning-report `flash` was gated on `queue.length === 0` — correct-looking in isolation (don't show a report behind/instead of a decision) but wrong given the UI actually stacks the two overlays by z-index, so the gate just threw away a fully-built report on any day a decision also queued. Caught by counting flash-present vs flash-empty days across a scripted run, not by type-checking. When a day-derived value (`reportLines`, `flashLines`, etc.) gets built unconditionally but attached to state conditionally, check what the UI actually does before assuming the condition is load-bearing.
4. **An "eligible" filter that's too conservative can starve a trigger indefinitely.** Excluding a horse from Classic/Diamond Cup eligibility for having *any* pending entry (rather than a real date conflict) meant an aggressively-played auto-loop ran to year 3 without the Classic trigger ever firing once — caught only by extending a scripted-playthrough script's day budget far past where the trigger "should" have fired and asserting it actually did, not just that it didn't fire too early. When a self-healing "wait until eligible" trigger never seems to fire in a long test run, suspect the eligibility filter's precision before suspecting the trigger's timing logic.
5. **`Object.keys()` on a mixed number/string-keyed object silently stringifies numeric keys, and a TypeScript cast doesn't fix it.** `makeRoster()` iterated `Object.keys(CLASS_STATS)` (`Record<3|4|5|6|"L"|"G3"|"G2"|"G1", ...>`) with an `as (keyof typeof CLASS_STATS)[]` cast — that cast only tells the type checker to trust you, it does not change that `Object.keys()` returns `string[]` at runtime. Every roster horse in the numeric bands got a stringified `rosterBand`, permanently mismatching every real numeric `Grade` comparison elsewhere. Fixed by iterating a separately-declared, correctly-typed array (`BAND_ORDER`) instead of deriving keys from the object at runtime. Any time an object has both numeric and string keys and something needs to iterate/compare those keys by value (not just use them for property lookup, which does coerce fine), don't trust `Object.keys()` to preserve the original type.
6. **JSX can silently eat a space between `{expression}` and adjacent literal text on the same line** in this project's Next.js/SWC setup (see `AGENTS.md`'s warning that this isn't stock Next.js). `{yard.boss} won't...` compiled to a DOM text node reading `"won't..."` with no leading space — confirmed via direct `childNodes` inspection, not just visual inspection (a zoomed screenshot of tight monospace text can look like it has a space when it doesn't). The robust fix is a single template-literal expression (`` {`${yard.boss} won't...`} ``) instead of mixing `{expr}` and literal text as separate JSX children. Worth checking any other `{expr} literalText` pattern in this codebase if new ones are added.
7. **A function invoked exclusively through another wrapper doesn't need its own copy of what the wrapper already does.** `resolveRaceDay()` is only ever called through a "Riding instructions" decision's `apply()` — so it never needed its own threshold-crossing check; `chooseDecision()`'s wrapper (added for exactly this purpose) already runs on every decision's result, `resolveRaceDay()`'s included. Having both duplicated the message and doubled the cash reward. Caught via a long (600-day) scripted playthrough, not a short one or `tsc`/lint — before adding a cross-cutting check to a low-level function, check whether every call site is already wrapped by something higher up that could do it once instead.
8. **An array that's *usually* non-empty can become empty as the game state evolves, and `pick([])` won't tell you.** `makeSlate()`'s "away" race (`pick(away)`, `lib/sim/race.ts`) crashed once Reputation cleared the tier-2 unlock threshold: `unlockedCourses()` then returns *every* course, so `away` (courses not already "home") becomes empty, and `pick([])` returns `undefined`, crashing on the next property access. Only surfaced in a 600-day scripted playthrough that kept Reputation elevated for long enough — short test runs or early-game testing would never hit it. When a `pick()`/array-index call's source array is derived from something that changes over a playthrough (unlocks, milestones, etc.), don't assume "it's always had items in every test so far" means it always will.
9. **A "pick one" assignment can silently clobber everything queued earlier the same tick, and the failure mode looks fine in short tests.** `advanceDay()`'s day-content roll did `queue = [tm]` for its ~30% decision-day branch — everywhere else in the function appends (`queue = [...queue, x]`), but this one line replaced the array outright, wiping out any going-change decision, race-tactics decision, or (once added in round 5) vet-bill decision already queued earlier in the same `advanceDay()` call. Races self-healed (a still-entered, still-overdue race just rebuilds its tactics decision next tick, so the loss was invisible in play), which is exactly why it went unnoticed through four previous rounds of scripted testing — only a genuinely one-shot queued decision (the new vet bill) exposed it, because that one doesn't come back. When auditing a function that both builds up a list across several early-exit-free sections *and* has one branch that assigns to that list instead of appending, check whether the assigning branch runs after the appending ones — and don't trust "no crash in a long scripted run" to mean "no queued item ever got dropped," since a self-healing queue item hides exactly this class of bug.
10. **Deriving a cosmetic ordering from `id` silently encodes creation order, not randomness.** `computeRaceTrack()`'s lane assignment sorted the field by `horse.id` ascending — looked like an arbitrary-but-stable tie-break, but the player's horse is always among the first handful of `nid()` calls in a new game (the 6 starting candidates), while every rival is drawn from a ~120-horse roster generated afterward. The result was deterministic, not random: the player's horse had the lowest id in nearly every field, every race, for the life of a save. Nothing about the code looked wrong in isolation — `sort by id` reads as neutral — and it took a playtester noticing the pattern across several races (not a crash, not a type error) to catch it. When a "stable, arbitrary" ordering is derived from an autoincrementing id and the population being sorted was seeded in two batches at very different times (a handful of low-id "special" entities plus a large later-generated pool), check whether that ordering secretly correlates with which batch something came from.

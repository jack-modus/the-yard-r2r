# The Yard: Rags to Riches

A horse-racing trainer sim (Next.js App Router + TypeScript + Tailwind v4, PWA target). The player is Tony Vincenzo — a fixed protagonist, not a customisable name — taken on by trainer Simon Bridges despite (or because of) his father's disgraced history in the sport, working toward a Group 1 win with a string built up one horse at a time, starting from a single pick out of six candidates. Originally prototyped as a single-file Claude.ai JSX artifact (`reference/rags-to-riches-v6.jsx`) — that file is kept for reference during extraction, is not linted as app code, and should not be imported from.

## Hard rules — do not violate these

1. **No real named people.** Rivals, jockeys, trainers, bosses, owners — all fictional, real-sounding names only. Never use a real person's name, even a retired or minor one. This avoids IP/publicity-rights risk. **Exception, by explicit user decision**: the five real British Classics (1000/2000 Guineas, Oaks, Derby, St Leger) are used by their real names in `lib/sim/calendar.ts` — these are historic race *traditions*, not people, so the publicity-rights logic behind this rule doesn't apply the same way. Don't extend this exception to other real-world racing entities without asking; it was a specific, explicit call for the Classics only.
2. **Course/track facts must be factual but never copied.** Course descriptions (`src/lib/sim/courses.ts`: `COURSES[...].line`, `INSIGHTS`) and draw-bias notes must be written fresh from general racing knowledge. Never lift wording from Racing Post, Timeform, or any other source verbatim or near-verbatim. Facts (e.g. "Chester is left-handed and tight") aren't copyrightable — expression is, so always re-derive the description in original words.
3. **No live scraping of commercial racing data.** Never scrape or ingest Racing Post/Timeform/etc. results data — ToS/licensing risk. The only real-world dataset permitted is the user's own historical race data in `C:\Users\jackr\ggs` (their existing Betfair ML pipeline), used to calibrate the sim's invented stat curves against real favourite strike-rates and SP distributions — never to source real horse/human names or copy real race commentary.
4. **No monetisation linked to the simulated betting.** Do not add a paid "Hall of Fame," loot boxes, or any real-money purchase connected to in-game wagering or chance outcomes — regulatory risk, worse given minors could plausibly access it. If monetisation is revisited later, the only acceptable pattern is flat-price cosmetic/commemorative items that are never linked to chance or convertible into in-game stakeable currency.
5. **Deployment target is a PWA** (installable website via Next.js/Vercel), not a native app store submission. Don't introduce native-only APIs or a native wrapper without an explicit decision to revisit this.

## Architecture

- `src/lib/sim/` — the race simulation core. Pure, React-free, fully typed. `expected()`/`runRace()` (race.ts), `makeHorse()`/`makeCandidateHorses()` (horse.ts), gear effects (gear.ts), `courses.ts` (course data + `TIER1_COURSES`/`TIER2_COURSES`), `yards.ts` (the single `YARD` trainer, Simon Bridges), plus `classStats.ts` (real-data OR/field-size distributions per class) and `roster.ts` (the persistent NPC horse pool — see "Historical data" below).
- `src/lib/game/` — the game state machine sitting on top of `lib/sim`. `engine.ts` holds `newGame`/`resolveHorsePick`/`advanceDay`/`resolveRaceDay`/`chooseDecision`/`enterRace` as pure functions over a typed `GameState`; `tracks.ts` holds `unlockedCourses()`/`REPUTATION_TIER2_UNLOCK`; `content.ts` holds ordinary day-content generators (`trainingMoment`, quiet-day/news lines); `story.ts`/`storyContent.ts` hold the entire scripted narrative — Act 1's nemesis arc, Act 2's Classics, Act 3's Diamond Cup/father subplot/ending (see "The scripted narrative" below); `storage.ts` is the localStorage save/load layer.
- `src/components/` — the UI. `intro/` (`IntroScreen` — opening image only, no name entry; `HorsePickScreen` — single-select from the 6 candidates, see "Horse acquisition" below), `game/` (header, four overlays — daily flash, decision, live race, help — tab bar, four tabs, advance bar, `EndingScreen` — career summary + share card), `ui/` (small primitives: Card, StatBar, PlanButton, Button).
- `src/app/page.tsx` — top-level orchestration: owns `GameState`, wires engine calls to UI callbacks, handles localStorage load/save.
- Styling: Tailwind v4 with custom `@theme` tokens in `src/app/globals.css` matching the original prototype's dark-purple-and-gold racing-diary palette (`ink-*`, `gold-*`, `parchment-*`). `font-diary` = Georgia serif (narrative text), `font-mono` = Courier New (UI chrome/numbers) — this mirrors real racecard typography conventions the prototype was built around.

## Tuned sim constants — validate before changing

The noise/spread constants below are calibrated against real outcomes from `ggs/races_master_v4.csv` (see "Historical data"), not hand-tuned by feel. If retuning, regenerate the grid-search rather than eyeballing it — the first attempt at this (the prototype's original 0.05-0.22 noise range) produced a 75% simulated favourite strike rate against a real 34.1%, which is exactly the kind of error that "feels roughly right" until you check it against data.

- **Race-day noise**: `noiseSd(h) = clamp(0.735 - (temperament/100)*0.315 + gearNoise, 0.26, 1.16)` (`lib/sim/race.ts`). This is the prototype's original formula scaled ×5.25 — that scale factor was grid-searched to match the real 34.1% favourite strike rate (n=2142 favourite-marked runners, tier-1 courses). Gear `noiseAdj` values in `lib/sim/gear.ts` are scaled by the same ×5.25 so gear's relative effect on consistency doesn't round to nothing.
- **Roster field-composition band width**: exact match on `Horse.rosterBand`, not OR-value proximity. An OR-window filter (even ±0.5 std) was tested and let neighbouring class bands' Gaussian tails bleed into each other, inflating a single race's effective rating spread — the calibration above assumes single-band fields, so the filter has to actually produce them.
- **Softmax temperature**: `3.2` in `runRace()`'s odds calculation — controls the displayed SP *spread* across the field, not who wins (win/lose is decided by the noisy `score`, and softmax is order-preserving, so the SP favourite and the noisy-score favourite are always the same horse). Not yet validated against the real odds-bucket calibration table pulled during analysis; lower priority than the win-rate fix since it's cosmetic.
- **Course-interaction weights** (`expected()` in `lib/sim/race.ts`): sharpness penalty ×0.035, undulation penalty ×0.03, finish-climb penalty ×0.04, break bonus ×0.06 (sprints ≤6f) / ×0.02 (longer), course mastery worth up to 5% (`×0.05`). Not recalibrated against real data yet.
- **Injury base rates**: gallop/sprints training = `0.02 + (fatigue/100)*0.05` per day (`engine.ts`); stalls-practice decision = 10%; "let it stretch out" decision = 12%.
- **Handicapper mark deltas** (`resolveRaceDay` in `engine.ts`): win by ≥2.5L → +6 to +9lb; any win → +3 to +6lb; close-up place (gap <1L) → +1 to +3lb; well-beaten (gap >4L) → -3 to -6lb; moderate effort (gap >2L) → -1 to -3lb.
- **Day-content roll** (`advanceDay`): 35% quiet flavour line, 15% news line, 30% decision event (`trainingMoment`), 20% nothing — raised from the original 42/18/18/22 split per playtesting feedback that the early game felt too thin.

## Historical data

`C:\Users\jackr\ggs` holds the user's own Betfair ML pipeline. The dataset actually used so far is `races_master_v4.csv` (real flat-racing results, 2022-2026, ~530k rows) — the dated `*racecard.csv` files and `betfair_2026_results.csv` are 2026-only and weren't needed for this pass. This is the *only* permitted source of real racing data (see hard rule 3); only aggregate numbers (mean/std of OR and field size per class) were pulled out, never real horse/trainer/jockey names or comment text.

**What's wired in**: `lib/sim/classStats.ts` holds real per-class OR mean/std and field-size mean/std (tier-1 courses: Newmarket, Goodwood, Sandown, Epsom Downs — "Class" in British racing is a national ability band, not course-specific, so this generalizes to races at any course). `lib/sim/roster.ts` uses it to seed a ~120-horse persistent NPC pool (`GameState.roster`, created once per new game in `newGame()`) instead of inventing a throwaway field from scratch every race — this is what makes rival horses recur across a season with an evolving win/run record, and it's what the noise calibration above was validated against. `G3`/`G1` bands in `classStats.ts` are informed extrapolation (the dataset lumps all Group/Listed races into one "Class 1"), flagged inline for future recalibration if a Pattern-race-only sample becomes available.

**Not yet done**: applying this same real-data approach to non-flat/other calendar specifics, and recalibrating the softmax temperature and course-interaction weights the same rigorous way (both currently just carried over from the prototype).

## Single trainer + track tiers

The original 3-boss/yard picker is gone — `lib/sim/yards.ts` exports one `YARD` constant: Simon Bridges, Newmarket, built around the backstory in the Act 1 opening (he trained alongside Tony's grandfather; Tony's father gambled the family name away). The previous passes' placeholder personas (Marina Delacroix-Hale, Frank Berrow, Sonny Okafor) weren't deleted — they're folded into `RIVAL_TRAINERS` in `lib/sim/race.ts` so their writing still surfaces in race results instead of being wasted. Martin McLean is deliberately **not** in that pool — he's a persistent nemesis tied to one specific horse; see "Act 1 scripted narrative" below.

Courses are split in `lib/sim/courses.ts`: `TIER1_COURSES` (Newmarket, Epsom, Sandown, Goodwood) are open from game start; `TIER2_COURSES` (Ascot, Doncaster, York, Chester — Doncaster specifically so the St Leger is something to build to) unlock once Reputation clears `REPUTATION_TIER2_UNLOCK` (35, in `engine.ts`). `unlockedCourses(reputation)` is the single source of truth for what's open — used by `makeSlate()`'s course pool and by `NotebookTab`'s lock-gating. There's no more "your yard's home tracks" concept; the player starts with a little course mastery at all four tier-1 tracks instead of two.

## The four metrics

Two families, deliberately separated: three "who's judging you" axes (perception) and one "what you actually have" axis (capability). This is the user's own design spec (verbatim reasoning kept here since it explains *why* each rule exists, not just what it does) — implemented in `resolveRaceDay`/`advanceDay` in `engine.ts`, surfaced in `YardTab` and the header.

1. **TRUST** — one person's private opinion of you (the boss specifically, not the wider world). Can go down. Critically, it's movable by things that aren't race results (the targets-vs-process conversation, the press-quote choice indirectly, etc.) — that's what keeps it from feeling redundant with Reputation. Gates: second horse, trade-up offers, entry to bigger races. Unchanged from the original prototype.
2. **REPUTATION** — what insiders (jockeys, other trainers, owners, the handicapper) think of your ability. Lagging, results-driven, grade-weighted (`gradeWeight()` in `engine.ts`: a G1 win is worth 18, a Class 6 win is worth 1). Can go down on a bad-beat run. Gates tier-2 track access. *New this pass* — the design was described in earlier project notes but had never actually been built; don't assume it existed before this.
3. **CELEBRITY** — public/media profile, distinct from insider respect. Deliberately pulls *against* Reputation: the new "local paper wants a word" `trainingMoment` event (`content.ts`) is a genuine trade-off (big quote: +celebrity, -reputation; modest quote: +reputation only), not a free top-up. Big-race wins (G1/G2) also bump it a little ("hyped horses"). **Not yet wired into the sim**: the spec calls for Celebrity to nudge a horse's market SP shorter independent of true ability (public sentiment moves markets in real racing, creating a "smart money vs public money" dynamic) — deliberately deferred rather than bolted on same-session, since it touches the `runRace()`/softmax odds math that was just carefully calibrated against real data (see "Tuned sim constants"); redo the grid-search validation if this gets built.
4. **SKILL** — the trainer's own accumulated capability. Never falls — framed as an XP bar, not a score, specifically to give a losing streak something that still goes up. Grows from volume of practice (any active training day +1, a race run already gives +3 via Reputation-adjacent logic, a course walk +4), caps at 100. Scales training effectiveness up to +30% (`skillMult` in `advanceDay`) — this is literally the same hidden `trainMod`-style constant the spec calls out, just surfaced as a real, player-visible stat instead of staying buried. Further gates (faster hidden-trait reveals, spotting a well-handicapped horse before the market) are designed but not built.

**Playtesting note**: a synthetic auto-play bot (train one stat only, always accept the first offered race, always pick the first decision option) went 0-for-33 over one test run and reputation sat at the floor — plausible given how deliberately weak an untrained horse starts and how single-minded that training strategy was, but flagging it as worth a real human playtest for pacing/difficulty rather than assuming the numbers are already well-tuned. This 0-for-many pattern reproduced again in a later scripted-playthrough run (900 simulated days, single-stat "gallop" training, always "hold up" tactics) — treat it as an accepted, already-flagged characteristic of naive/single-minded play, not a new regression, unless a future human playtest says otherwise.

**"Reveal after, not before" (per playtesting feedback)**: `Choice.hint` on any decision that moves Trust/Reputation/Celebrity/Skill is deliberately omitted — the player commits to a choice without seeing its metric impact in advance, then the impact is revealed as an explicit `(Metric ±N.)` suffix appended to the post-choice narrative text (`note()`'s text argument). This applies across `content.ts` and `storyContent.ts`. It does **not** apply to `hint`s describing a mechanical/training choice (which stat a horse trains, which track gets studied, physical +stat/+fatigue effects) — those aren't "moral choice" reveals, they're the entire visible point of a resource-allocation decision, and stay visible before the choice (e.g. `BEAT7_BRIDGES_ADVICE`, `makeBeat8AllyTrainer`).

## The scripted narrative (Tony Vincenzo, Simon Bridges, Martin McLean)

This is the fix for the "biggest known design gap" flagged early on — real branching narrative and a persistent rival, not just ambient random content. The whole arc (Act 1 nemesis intro → Act 2 Classics → Act 3 Diamond Cup/father subplot → ending) was planned and built across two passes; this section is the load-bearing summary for future changes, not a duplicate of the approved plans (`~/.claude/plans/replicated-sleeping-sedgewick.md` has the original scoping detail if ever needed, but treat this section as authoritative over that file, which isn't updated after the fact).

### Act 1: the opening + the nemesis

**Flow**: `IntroScreen` (opening image, no input) → `newGame()` seeds `GameState.queue` with beat 2 (Bridges' office — an internal, consequence-free "grandfather or father?" question) → beat 2's choice enqueues beat 2b (Ray Fenwick, the head lad — pure characterisation, added because the jump straight from office to horse pick felt too rushed in playtesting) → beat 2b enqueues beat 3 (yard scene with jockey Rossa Bellini, "will you win your first one?" — real reputation/celebrity deltas) → beat 3 sets `awaitingHorsePick`, which `page.tsx` renders as `HorsePickScreen` (single-select from the 6 `horseCandidates` `newGame()` generated — see "Horse acquisition" below) → `resolveHorsePick()` schedules the nemesis intro and normal play begins. `GameState.story.stage === "yard"` is what tells `page.tsx` to render the minimal pre-game chrome instead of the tabbed shell; everything from `"preNemesis"` onward fires through the ordinary `DecisionOverlay`/`DailyFlashOverlay`, same as any other content.

**The nemesis (Martin McLean, McLean Racing, Middleham)**: a rival *trainer*, not jockey — deliberately given his own persistent mount (`story.nemesisHorseId`, added to `GameState.roster` when he's introduced, always tagged `trainerName: "Martin McLean"` via `ensureNemesisInField()` in `story.ts` rather than the normal randomized trainer-name assignment other roster horses get). Introduced ~4-6 days after the horse pick (`scheduleNemesisIntro()`: `day + ri(3, 5)`, beat 4, flash-only) — deliberately early, per playtesting feedback that the hook needed to land sooner (previously ~7-10 days). His mount is then **forced** into the player's next declared race — `story.forceNemesisNextRace` — with a pre-race reporter decision (beat 5) and a **guaranteed loss**: `forcePosition()` in `story.ts` swaps scores after `runRace()` computes a normal result, so the scripted defeat still looks like a physically coherent race, not an obviously fake one. Beat 6 (McLean's taunt) follows immediately. A second meeting fires ~110-130 days later (beat 9) — McLean is forced into the field again the same way, but this time the outcome is genuinely probabilistic (verified: both a player win and a nemesis win occur across repeated test runs). `story.headToHead` tracks the record across both. Beats 7 (Bridges advice — pick a stat, all horses improve) and 8 (ally trainer Callum Rees — pick a track, big mastery jump) fire in between on their own day-triggers.

**Horse acquisition**: the player starts with exactly **one** horse (single-select `HorsePickScreen`, not the original 3-of-6), and grows the string on race results rather than Trust — per playtesting feedback that the original 3-horse start made the first choices feel inconsequential. In `resolveRaceDay()` (applies uniformly to ordinary races, Classics, and the Diamond Cup — not gated to any one race type): a top-3 finish (`mine.pos <= 3`) grants a second horse (`milestones.secondHorse`); once total wins across the whole string (`horses.reduce((sum,h)=>sum+h.wins,0)`) reaches 3, a third horse is granted (`milestones.thirdHorse`). The old trust≥45-gated second-horse trigger in `advanceDay` was removed; the separate trust≥75 trade-*offer* mechanic (swap a horse for a better one) is unrelated and unchanged.

### Act 2: the Classics

Once Act 1 reaches `story.stage === "ongoing"` **and `GameState.year >= 2`** (see "Multi-race declarations..." below for why this gate exists and how it's enforced), the Classics run on their **own independent CALENDAR-day schedule** — the two arcs deliberately overlap in real time (McLean's second meeting can land mid-Classics) rather than waiting on each other. `CALENDAR` in `lib/sim/calendar.ts` holds the five real Classics (see hard rule 1's exception); each one's own mini-arc lives in `story.ts`/`storyContent.ts`: a dynamic horse-choice decision (`story.classicArc`, ~20-40 days out depending on which Classic), McLean entering + media doubts folded into one decision, an automatic top-jockey booking (a temporary `jkSkill` boost tied to `race.isClassic`, not tracked as separate state — "eventually the top jockey takes the horse" is treated as inevitable), the race itself fully probabilistic, then a **four-way outcome branch** (win/place/okay/tank) via `classifyClassicOutcome()`/`resolveClassicOutcome()`, with **diminishing-returns-scaled** deltas (`CLASSIC_DIMINISH = [1, 0.7, 0.5, 0.35, 0.25]` across the five). Results accumulate in `story.classicResults`, which an occasional press-callback (`makeClassicCallback`, folded into the ordinary `trainingMoment` pool) can reference later.

**Balance bug caught via testing**: tagging all five Classics grade `"G1"` for real-world authenticity meant every one drew opponents from the real-data G1 band (mean rating ~108) regardless of each Classic's own `minOR` (76-94) — every test run came back "tank". `grade` in `CALENDAR` is a gameplay dial selecting the opponent-strength band (see `roster.ts`), not a strict real-world label — it now escalates L/G3/G2/G1/G1 across the five, matching the original (pre-Classics-rename) calendar's validated balance, while keeping the real race *names*.

### Act 3: the Diamond Cup, the father subplot, the ending

Begins once `story.classicIndex` reaches 5 (all Classics resolved) — scheduled on **relative** "days since the previous beat" (`story.diamondCup.nextBeatDay`/`raceDay`), not fixed calendar days, since it's scripted-only with no `CALENDAR` entry backing it. Sequence: announcement (a fictional one-off prize, deliberately bigger than the Breeders' Cup, `DIAMOND_CUP_PRIZE` — completely outside the normal `PRIZE` table) → McLean entering → the father subplot (Michael Vincenzo backs McLean for a paid-off quote, then a confrontation scene — accept the apology vs air it in the press, real trust/celebrity trade-off) → horse choice → an injury scare that resolves as a false alarm (flavour only, never touches `injuryDays`) → the race itself, biggest deltas in the game (`resolveDiamondCupOutcome()`), no diminishing returns since it only happens once.

Once the Diamond Cup resolves, `computeEnding()` evaluates the final Trust/Reputation/Celebrity: Trust ≥60 → contract extension (`"contract"`); else Reputation or Celebrity ≥50 → poached by a rival trainer (`"poached"`, deliberately reuses Marina Delacroix-Hale rather than inventing a new name); else released (`"released"`). `page.tsx` renders `EndingScreen` once `GameState.ending` is set (gated on `!g.liveRace` so the Diamond Cup's own commentary plays out first) — a career summary (final four metrics, Classics list, Diamond Cup result, McLean head-to-head, horses' records) plus a client-only share card (`navigator.share` with a clipboard-copy fallback — no backend, per explicit user choice; there isn't one for this project yet).

### Daily morning report + UI variety (per playtesting feedback)

`advanceDay()` builds a `reportLines: string[]` array — per-horse training-type and the resulting primary stat value (or injury-recovery status), a course-walk summary, a skill-increase line, and a new-race-slate line — concatenated with the day's ordinary messages/news into `flash: string[] | null`. This is **always** attached when non-empty (`flash: flashLines.length ? flashLines : null`), including on a day that also queues a decision: `DecisionOverlay` (z-31) renders over `DailyFlashOverlay` (z-30), so the report surfaces automatically right after the decision is dismissed rather than being dropped. Before this pass the flash was gated on `queue.length === 0`, silently discarding a fully-computed report on any day a `trainingMoment` decision also fired (~30% of days) — caught via a scripted-playthrough run showing ~14% of days with no flash at all.

`DecisionEvent.tag?: DecisionTag` (`"PRESS" | "BOSS" | "RIVAL" | "TRAINING" | "FAMILY" | "YARD"`) is a purely cosmetic category label — `DecisionOverlay` uses it to pick a border/pill accent colour (`TAG_COLOR` map) so decisions don't all render identically, per feedback that the UI felt "very samey." Every `DecisionEvent`/factory in `content.ts` and `storyContent.ts` is tagged; it has no effect on game logic.

### Multi-race declarations, rival visibility, and metric glanceability (round 2 playtesting feedback)

A second real playtest ("a few weeks" of game-days) surfaced a core "grind" complaint traced to two causes, both fixed together:

- **`GameState.entered` was a single slot for the whole yard.** Declaring one horse into a Classic (scripted weeks ahead) blocked every other horse from racing until that one race day arrived. `entered` is now `EnteredRace[]` — one entry per horse, not one for the whole yard. `enterRace()` pushes onto the array (also computing that entry's `fieldPreview`, see below) instead of overwriting, and only removes the just-declared race from `slate` rather than clearing the whole thing. `advanceDay()`'s going-change and race-day checks loop over all due entries instead of early-returning on the first (and only) one — a horse whose race lands today no longer blocks the rest of the string's training/report that day. `resolveRaceDay(st, tactic, raceId)` takes an explicit race id now, resolving just that one entry. `RacingTab.tsx` renders one Declared card per entry, alongside the slate (not either/or), with each button filtering out horses already entered elsewhere.
- **The Classics ran in year 1**, almost immediately after the single-horse start — no time for the results-based string-building above to matter before the biggest scripted races arrived. They're now gated to `year >= 2` in `story.ts`'s `checkStoryTriggers()`. Because `day` is day-of-year (resets every year) and nothing previously checked `year` anywhere in the trigger/race-day logic, this **had** to be an explicit year check — retuning `CALENDAR`'s `day` values would not have worked, since year 1 day 50 and year 2 day 50 are indistinguishable to a day-only comparison. `RacingTab.tsx`'s big-race calendar tab has its **own separate manual-declare path** into a Classic (bypassing the scripted horse-choice arc entirely) that needed its own identical year gate, or the year-2 requirement could just be sidestepped by declaring from that tab instead.
- **Eligibility filtering for the Classic/Diamond Cup horse-choice trigger must only exclude real scheduling conflicts, not "has any entry at all."** An early version of the year-2 fix excluded any horse with *any* pending entry from Classic eligibility — since ordinary bookings almost always resolve weeks before a Classic's own fixed date, an active player who keeps every horse booked into near-term races (exactly what multi-race declarations are meant to encourage) could starve the trigger indefinitely. Fixed by only excluding a horse if its existing entry's `raceDay` is within ~10 days of the Classic's own `raceDay` — see bug class 4 below.
- **Rival field preview**: each declared race gets a one-off, indicative `fieldPreview` (name/trainer/mark for the likely opposition), computed once at declare time via the same `drawField()` roster machinery races already use (`engine.ts`'s `enterRace()`, plus the same logic duplicated in `storyContent.ts`'s `makeClassicHorseChoice`/`makeDiamondCupHorseChoice` since those also create entries directly). It's deliberately *not* the exact field `resolveRaceDay` later draws — reusing/locking a field would also need to replicate the McLean forced-insertion timing, real complexity for a "just show me the competition" UI want. Results also now show every finisher, not just the top 6 (`resolveRaceDay` no longer slices `res` before storing it).
- **Header now shows all four metrics with a cosmetic rank label** (`lib/game/ranks.ts`'s `metricRank()`: Unproven/Rising/Established/Elite/Legend at 0/20/40/60/80) — previously only Trust/Reputation were in the header at all, Celebrity/Skill were YardTab-only. This is the direct answer to "what happens at 100": the metric still hard-caps, the rank name is what communicates that the cap means something. A genuine next step the user raised — trading further gains from an already-maxed metric into the others — is **not built**: it would need every inline `clamp(st.X + n, 0, 100)` call site across `content.ts`/`storyContent.ts`/`engine.ts` migrated to a shared helper that can detect and redirect overflow, a large, separable refactor left for its own pass.
- **`resolveRaceDay()` now states its own Trust/Reputation/Celebrity deltas** as an explicit message (`Trust +N, Reputation +N, Celebrity +N.`, only pushed when at least one actually changed) — previously only decision outcomes got this "reveal after" treatment; race-day changes happened silently.
- **Decision-outcome toast**: the reveal-after delta text has always existed (`note()`'s message), but was only ever visible by manually opening the Yard tab's message log — no immediate on-screen confirmation after choosing. `page.tsx` now captures the just-resolved decision's outcome message into local (non-`GameState`) UI state and shows it as a dismissable banner at `z-[35]` — above `DecisionOverlay` (z-31) and `DailyFlashOverlay` (z-30) — so it's the first thing shown, then dismissing it reveals whatever's queued next. Deliberately not wired into the pre-horse-pick intro screens (`story.stage === "yard"`), since no metrics are visible there yet.

### Bug classes worth remembering (caught by scripted-playthrough testing or manual browser verification, not `tsc`/lint/build)

1. **Uncleared day-triggers re-fire infinitely.** `advanceDay` doesn't increment `day` on a tick that queues a scripted beat, so any day-gated trigger (`story.bridgesAdviceDay`, `allyTrainerDay`, etc.) must null out its own trigger field the moment it fires, or it re-queues the same beat forever the next time `advanceDay` runs.
2. **A scripted race can be scratched.** If the horse declared for a Classic or the Diamond Cup gets injured before race day, the ordinary scratch path (`advanceDay`'s race-day check) just cleared `entered` and moved on — but nothing else ever resumed that arc, permanently stalling Act 2/3 (`classicArc`/`diamondCup` stuck mid-stage forever, `story.classicIndex` never reaching 5). Fixed via `skipClassic()` (a scratched Classic is a missed calendar date in real life — no stat penalty, just move to the next one, recorded as a `"scratched"` `ClassicOutcome`) and `rescheduleDiamondCup()` (no fixed calendar date, so just try again ~15 days later). Any new day-gated or scripted-declaration content should be tested against "what if the chosen horse gets injured mid-arc" specifically.
3. **A per-day computed result silently discarded by an unrelated condition.** The morning-report `flash` was gated on `queue.length === 0` — correct-looking in isolation (don't show a report behind/instead of a decision) but wrong given the UI actually stacks the two overlays by z-index, so the gate just threw away a fully-built report on any day a decision also queued. Caught by counting flash-present vs flash-empty days across a scripted run, not by type-checking. When a day-derived value (`reportLines`, `flashLines`, etc.) gets built unconditionally but attached to state conditionally, check what the UI actually does before assuming the condition is load-bearing.
4. **An "eligible" filter that's too conservative can starve a trigger indefinitely.** Excluding a horse from Classic/Diamond Cup eligibility for having *any* pending entry (rather than a real date conflict) meant an aggressively-played auto-loop ran to year 3 without the Classic trigger ever firing once — caught only by extending a scripted-playthrough script's day budget far past where the trigger "should" have fired and asserting it actually did, not just that it didn't fire too early. When a self-healing "wait until eligible" trigger never seems to fire in a long test run, suspect the eligibility filter's precision before suspecting the trigger's timing logic.
5. **JSX can silently eat a space between `{expression}` and adjacent literal text on the same line** in this project's Next.js/SWC setup (see `AGENTS.md`'s warning that this isn't stock Next.js). `{yard.boss} won't...` compiled to a DOM text node reading `"won't..."` with no leading space — confirmed via direct `childNodes` inspection, not just visual inspection (a zoomed screenshot of tight monospace text can look like it has a space when it doesn't). The robust fix is a single template-literal expression (`` {`${yard.boss} won't...`} ``) instead of mixing `{expr}` and literal text as separate JSX children. Worth checking any other `{expr} literalText` pattern in this codebase if new ones are added.
